# 快运网络班车与货物路由滚动优化

本项目实现一个可复现的动态快运网络实验：常规货物在0、6、12小时到达；系统每6小时固定滚动重调度；每个异常算例最多在两个固定调度点之间发生一次紧急插单、紧急撤单或车辆故障，并立即增加一次事件重调度。

## 静态网页演示

`web` 目录实现了 Vite + React + TypeScript 单页展示站点，包含固定模型结构、全局与实例参数、三种方法技术路线、统一结果图表、三联动画及证据边界。页面只读取预处理JSON，不会在浏览器中调用优化代码。

```powershell
python scripts/build_web_data.py
cd web
npm install
npm run dev
```

完整的数据更新、构建与GitHub Pages发布说明见 [`web/README.md`](web/README.md)。

## 已冻结实验规模

- 8个分拨节点、12条双向物理连接、一种20等效吨车型。
- 内部时间刻度3小时，固定滚动间隔6小时，最长观察72小时。
- 4个小型正确性验证算例。
- 80个独立验证算例（供后续学习方法训练/调参流程使用，不进入正式测试）。
- 保留20个冻结测试母集：正常波动、紧急插单、紧急撤单、车辆故障各5个。
- 当前正式演示固定使用其中12个算例，每类按编号排序取前3个；所有方法必须使用同一清单，不得使用这12个测试算例训练或调参。
- 每类只有3个正式结果，统计量只用于描述方案表现，不作显著性或总体推断。

## 需求与异常

- 每批预测总量先按节点网络运力生成，再分配到OD×产品明细。
- 实际批次总量相对预测总量在±20%内波动；OD×产品占比再做±10%扰动。
- 6小时或12小时至少有一批出现不低于10%的预测偏差。
- 插单发生在15或21小时；撤单发生在3或9小时；车辆故障发生在3、9、15或21小时。
- 撤单总量由算例固定，事件发生时只从尚未发运的货物中确定撤单明细；车辆故障只从当时实际位于节点的可用自有车辆中选择。
- 节点拥堵不是独立随机事件，而是处理能力和积压共同形成的状态，由每次重调度自动处理。

## 服务水平与变更成本

- 所有未撤销货物最终送达仍是硬约束；产品准时服务率改为软约束。
- 低于98%/95%/90%目标的短缺吨数分别按1000/500/250成本单位每吨惩罚，目标不是硬性等式；所有晚到货物仍计算吨·时段延误成本。
- 每类需求最多仍保留36条候选行程，其中预留6条跨后续时段的延后行程；无法立即发运的货物允许跨夜留仓。
- 节点仓储能力假设充足，不设置仓容上限；节点分时段处理能力仍是硬约束。未能当期处理或发运的普通货物必须留仓至后续时段，并按2.5成本单位/吨·3小时时段计入留仓库存成本。
- 紧急插单的接入时刻由Gurobi显式决策，按“避免拒单→最早接入→最低运营成本”三级优先级求解，并输出立即接单、延后到最早可接时刻或72小时内无法接单。即使延后接入，服务计时仍从原始插单时刻开始。
- 每次滚动都比较上一版已发布计划，记录未来车辆任务变化和已规划货物改道；新到货物与撤单删除量不计货物改道。
- 最终比较使用完整运输、装卸、留仓库存、中转、延误、最终服务短缺惩罚以及全过程累计变更成本，避免只读取最后一次重调度。

## 动画数据记录

- 结果采用V6结构，日初计划和每次滚动重调度后都保存一份完整 `plan_snapshots`，滚动步骤通过快照ID连接调度前后方案。
- 每份快照保存已知需求与事件、班车任务、车辆来源及完整线路、货物分配行程，以及每个节点逐3小时时段的车辆数、处理量、留仓量、货物进出和班车进出。
- 节点时间线与完整货物行程会由验证器交叉核对；后续网页可以直接按快照顺序还原滚动动画，不需要重新调用优化代码。

## Gurobi协议

- 正式求解每次最多300秒，目标相对Gap为5%。
- 每个求解任务3线程，最多6个测试算例并行；采用动态任务队列，任一算例结束后立即补入下一个算例。12个算例约为6＋6两轮，总计最多18个Gurobi线程。
- 同一算例的网络服务和候选路径只生成一次，日初规划、周期滚动与事件重调度共享只读缓存；不同算例使用独立进程和独立缓存，不共享决策状态。
- 达到时限时保存 incumbent、best bound 和实际Gap；限时可行解不称为已证明最优。
- `TIME_LIMIT`且无可行解只表示300秒内未找到解，不等同于模型不可行。

## 一键运行

在PyCharm中打开根目录下的 `run_all.py`，点击运行即可。程序会：

1. 运行4个小型正确性验证算例；
2. 验证通过后，通过动态队列始终维持最多6个算例并行求解12个正式演示算例；
3. 自动独立校验每个完整结果；
4. 生成JSON汇总、统计分析和CSV明细。

中途停止后再次运行，会跳过已经完整写入的算例并继续。

主要输出位于：

- `results/verification/summary.json`
- `results/gurobi_v6_12/test/summary.json`
- `results/gurobi_v6_12/test/analysis.json`
- `results/gurobi_v6_12/test/case_metrics.csv`

## Benders＋列生成对比方法

在PyCharm中运行根目录下的 `run_benders_cg_all.py`，会先运行同一组4个小型正确性算例；全部通过后，再用同一份V6冻结清单运行12个正式算例。该方法与MILP使用相同的输入、班车任务、每批最多36条候选行程、业务约束、成本、滚动机制和独立验证器，只把求解过程改成外层整数Benders与内层连续货物列生成。

算法全过程直接写入每个结果的 `decomposition_trace`：包括主问题班车提案、上下界、割系数、每轮非零对偶、约化成本、新增列、人工变量、初始/最终列池、停止原因和各阶段时间。正式输出位于 `results/benders_cg_v6_12`。两种方法都完成后，可运行 `scripts/compare_milp_benders_cg.py` 生成逐算例配对比较。

算法控制参数单独放在 `config/benders_cg_config.yaml`，不会改动已冻结并带哈希校验的V6业务参数文件 `config/base_config.yaml`。当前第一版定价只在与MILP完全相同的有限候选行程池中动态加列，因此可以做严格公平对比，但不能声称搜索了候选池之外的全部时空路径。
