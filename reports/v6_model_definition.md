# V6 仓储充足与完整滚动快照修订

V6将仓储容量明确为建模假设：所有节点仓储能力充足，不设置仓储容量上限。冻结算例JSON中的 `storage_capacity` 仅为旧数据结构兼容字段，优化器和验证器均不把它作为可行性约束。

节点分时段处理能力继续作为硬约束。货物在0、6、12小时到达节点；当期处理能力或运输能力不足时，货物留仓至后续时段。普通未撤销货物必须在72小时观察期内全部送达。留仓按照2.5成本单位/吨·3小时时段收取库存成本；超过产品承诺时限后另计延误成本。中转操作成本、留仓库存成本和延误成本对应不同业务行为，不重复计费。

目标函数分项统一为：运输成本、货物装卸成本、留仓库存成本、中转成本、延误成本、服务水平短缺惩罚和方案变更成本。紧急插单仍采用“避免拒单、最早接入、最低运营成本”的分层决策。

结果结构升级为V6。日初规划以及每次周期或事件重调度后都保存完整计划快照。每份快照包括：

- 当前决策时点已知的需求与异常信息；
- 选中的班车任务、车辆来源、线路、发到时刻和车辆数；
- 每批货物的完整行程、每一运输段、留仓占用、中转和延期信息；
- 每个节点逐3小时时段的自有车辆数、处理量与利用率、留仓量与库存成本、货物进出、交付量、班车进出；
- 求解状态、运行时间、Gap、目标值及各成本分项。

每个滚动步骤记录 `plan_before_snapshot_id` 和 `plan_after_snapshot_id`，因此网页可以按快照序列还原“原计划—信息更新—新计划”的动画。验证器会检查快照完整性，并将节点处理量和留仓量与货物行程逐项交叉核对。

旧V5正式结果保留在 `results/gurobi`。V6正式演示从20个冻结母集中按编号固定选取每类前3个，共12个，结果写入 `results/gurobi_v6_12`，避免旧结果被误认为当前协议结果。
