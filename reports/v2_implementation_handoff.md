# V2 实现交付与异常记录

## 已完成

1. 将内部时间刻度由6小时改为3小时，同时保留每6小时固定滚动调度。
2. 常规货物只在0、6、12小时到达；实际批次总量围绕预测批次总量±20%波动。
3. 异常发生在固定调度点之间并额外触发一次重调度，后续固定调度点不取消。
4. 正式测试集缩减为20个，四类各5个；正确性验证缩减为4个。
5. Gurobi设置为单次300秒、目标Gap 5%、4线程，最多5个算例并行。
6. 新增根目录 `run_all.py`，负责冻结集校验、4个小验证、20个正式测试、续跑、独立验证和汇总。

## 实现难点

- 事件时点不能与6小时固定调度重合，因此内部时钟必须细化为3小时；所有旅行时间、产品截止期、处理能力、留仓与延误单位均同步换算，避免仅扩大时间索引却改变物理含义。
- 事件发生前不能提前进入模型。滚动求解在每个决策时点只披露已经到达的实际货量和已经发生的事件，并固定此前已经执行的车辆任务和货物流。
- 插单、撤单和故障不使用第二套目标或约束体系，而是在同一核心MILP中更新需求或车辆可用性，从而保持方法可比。
- 五个随机插单算例首轮恰好都抽到21小时；为避免展示单一，同时保持固定种子可复现，事件时点改为“固定种子随机打乱后均衡轮换”。

## 模型边界

- 这是聚合吨位候选路径MILP，不是逐票、逐车编号的生产级仿真。
- 节点拥堵通过处理能力、存储和积压状态体现，不作为第四类随机离散事件。
- 车辆故障表示指定节点在事件时点损失一辆可用自有车；若事件状态与硬约束共同造成已证明不可行，会如实记录。
- 300秒无 incumbent 只代表限时内未找到可行解；只有Gurobi返回 `infeasible` 才表示模型已被证明不可行。
